# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MeetingIntro is a macOS menu bar app (Swift 5.9 / SwiftUI, macOS 14+) that watches the user's calendar and, at configurable thresholds before each meeting, fires some combination of: a floating overlay with background music + a one-click Join button + a meeting context panel, a system notification with a Mixkit sound, and a spoken voice reminder. Firings are gated by live context (in another call, Focus on, screen-sharing, fullscreen app), the app can hand off audio output + Focus state on meeting start/end, and it can auto-record meetings with detected conference links to `.m4a` files in `~/Movies/MeetingIntro/`.

Distributed via Homebrew cask: `brew install --cask templegit9/tap/meetingintro`. Notarized + stapled.

## Build / run

Xcode project is **generated** from `project.yml` via [XcodeGen](https://github.com/yonaskolb/XcodeGen) — never hand-edit `MeetingIntro.xcodeproj/project.pbxproj`. **Info.plist is also generated** from `project.yml`'s `info.properties`; direct edits to `MeetingIntro/Info.plist` get overwritten on every `xcodegen generate`. Add new plist keys to `project.yml`.

```bash
xcodegen generate                                                  # regenerate .xcodeproj + Info.plist
open MeetingIntro.xcodeproj                                        # Xcode (⌘R to run Debug)
xcodebuild -project MeetingIntro.xcodeproj -scheme MeetingIntro -configuration Debug build
```

Bundle ID is `com.oluyinka.MeetingIntro`. `LSUIElement = true` — no Dock icon, menu bar only. Debug builds use ad-hoc signing (`-`) and no hardened runtime so they run without certs. Release builds use Developer ID + hardened runtime + `--timestamp` + `--options runtime` for notarization.

No test target. Verification is manual: open Settings → Countdown → **Test Countdown Overlay** for an in-app preview that exercises every overlay feature, or schedule a real calendar event a few minutes out and watch the live behavior.

## Releasing (Homebrew cask)

`scripts/release.sh <version>` does the full pipeline: regenerate project → build Release → sign → notarize → staple → re-zip → GitHub release → push cask to `templegit9/homebrew-tap`. Secrets load from `.env.release` at the repo root (gitignored). Full runbook in [RELEASING.md](./RELEASING.md).

**Measuring installs** — `scripts/downloads.sh` (table + totals + tap traffic; `--snapshot` appends a row to `metrics/downloads-history.csv`, `--history` prints it). **Homebrew analytics do NOT cover third-party taps** (only homebrew/core + homebrew/cask), so there is no `brew info --analytics` number for this cask — the proxies are GitHub release asset downloads (one per install/upgrade of a version; cached re-installs don't re-download, and the in-app self-update runs `brew upgrade`, so the newest version's count climbs for days after shipping) and tap clones (≈ first-time installs). GitHub keeps traffic for a **14-day window only and never backfills**, which is the whole reason `--snapshot` exists — run it periodically or that history is gone.

GitHub release notes are auto-generated: a "What's changed since <previous tag>" section is prepended to the install instructions from the commit subjects since the previous tag, grouped into New / Fixes / Other by conventional-commit prefix, with `chore: bump version` and `docs(claude-md)` bookkeeping filtered out. Capped at 30 commits. Commit subjects are themselves user-facing — write them accordingly. **The auto-generated list is a floor, not a ceiling.** Write the user-facing notes in **`docs/release-notes/<version>.md`** as part of the feature commit — `release.sh` picks it up by version (or `--notes <file>`), makes it the body of the release, and keeps the generated commit list beneath it in a collapsed "All changes" block. A missing file only **warns** (a release shouldn't fail for want of prose); an explicit `--notes` path that doesn't exist fails **before** the build, not after notarization. (Learned on v2.3.2, where an enhancement set shipped as half a subject line until retro-edited — then repeatedly after that, because post-release hand-augmenting depended on remembering: v2.16.1 and v2.16.3 went out un-augmented. Writing the file with the code removes the judgment call.)

**Signing gotchas that have actually bitten us** — keep these intact:
- `CODE_SIGN_ENTITLEMENTS: MeetingIntro/MeetingIntro.entitlements` in `project.yml` base settings. **Required** because `CODE_SIGN_INJECT_BASE_ENTITLEMENTS=NO` in Release turns off Xcode's automatic entitlement injection. Without the explicit path, the signed binary has zero entitlements and every capability (calendar, network, file pick) silently fails at runtime, regardless of TCC state. We shipped v1.0.0 through v2.0.4 with this bug; v2.0.5 fixed it.
- `OTHER_CODE_SIGN_FLAGS: "--timestamp --options runtime"` in Release. Notarization rejects signatures without a secure timestamp.
- `CODE_SIGN_INJECT_BASE_ENTITLEMENTS: NO` in Release. Otherwise Xcode injects `com.apple.security.get-task-allow` (the debugger-attach entitlement) and notarization rejects it.
- `Info.plist` uses `$(MARKETING_VERSION)` / `$(CURRENT_PROJECT_VERSION)` substitutions so the version the release script passes via `xcodebuild MARKETING_VERSION=$VERSION` actually reaches the bundle.

## Architecture

### App composition (`MeetingIntroApp.swift`)

`@main MeetingIntroApp` owns one `@StateObject` per long-lived service and exposes two scenes: `MenuBarExtra` and `Settings`. Services pass into views explicitly, not via the environment. The `audioRouter` / `handoffConfig` / `handoffCoordinator` trio is constructed together in `init()` because the coordinator needs references to the other two. `quickAddService` is also constructed in `init()` (sharing `qaConfig`) so the same instance is passed to both the menu content views and `observe()` — the conflict-provider wiring that previously lived in `QuickAddPanelController.calendarManager.didSet` now runs inside `observe()` step 1.

`AppLifecycleManager.observe(...)` is the **single wiring point**. Called once from `MenuBarView.onAppear`:
1. Wires `CountdownConfigManager` into `CalendarManager`, `MixkitSoundManager` into `NotificationManager`, attaches `handoffCoordinator` to `CalendarManager`, and wires `quickAddService.conflictProvider` to `CalendarManager.conflicts(start:end:)` (moved here from the retired `QuickAddPanelController`).
2. Defines one `@MainActor` `decide` closure: `(CountdownTrigger) -> ReminderDecision` that calls `ReminderEscalationPolicy.decide` with the live context snapshot. **The same closure is used for all three channels** (overlay, notification, voice) — single source of truth for the gating decision.
3. Wires the overlay channel via `calendarManager.shouldFireOverlay = { decide($0).showOverlay }`.
4. Starts polling (must happen *after* the hook is set so the first poll uses the policy).
5. Subscribes to `$shouldShowCountdown` for the overlay window, and to `$upcomingMeetings` for notification + voice fan-out (each gated by `decide(trigger)`).

If you add a new alert channel, wire it through `decide` here — don't sprinkle subscriptions across views.

### Calendar abstraction

`CalendarProvider` protocol (`CalendarProvider.swift`) unifies two backends:
- `EventKitProvider` — local macOS calendars via EventKit. Requires the `com.apple.security.personal-information.calendars` entitlement (declared in `MeetingIntro.entitlements`, wired via `CODE_SIGN_ENTITLEMENTS`).
  - **Subscribe to a Calendar by URL (v2.9.8)** — Settings → Calendar → "Subscribe to a Calendar by URL" (EventKit provider only). **EventKit has no ICS-subscribe API**, so `subscribeToCalendarURL()` normalizes an http(s)/bare/webcal link to `webcal://` and `NSWorkspace.open`s it — macOS Calendar runs its native subscription dialog (the user sets the refresh interval there). The subscribed calendar then appears in "Calendars to Monitor" to tick on; the Settings list reloads (`loadCalendars()`) a couple seconds after hand-off. **Two read-path gotchas surface here** (both by design, documented in the section's ⓘ): `fetchUpcomingEvents` drops all-day events (`EventKitProvider.swift` — no countdown to an all-day event), and the fetch horizon is `upcomingDaysAhead` (Menu Bar → Upcoming Days, default 7) — so a fixtures calendar spanning weeks shows "only some" until that's raised (max 30).
- `GraphCalendarProvider` — Microsoft 365 via Graph REST API using **OAuth device code flow** (a sandboxed menu-bar app doesn't have a reliable redirect URI). The Graph access token + expiration are stored in **Keychain** via `KeychainStore` (`MeetingIntro/Storage/`); the legacy UserDefaults values auto-migrate on first read after upgrade. Client ID stays in UserDefaults (not a credential). **Token refresh (v2.7.0):** `offline_access` yields a refresh token — now captured + persisted (`graphRefreshToken`) and used by `validToken()` to mint fresh access tokens transparently; all REST calls go through `validToken()` so reads no longer silently die ~1h after login (the pre-v2.7.0 bug — the refresh token was discarded). **Scope is `Calendars.ReadWrite`** (was `.Read`) so the provider can RSVP; the granted scope is stored (`graphGrantedScope`) and `supportsResponding` is true only when it includes write — a pre-upgrade token reports false until the user re-authorizes once (Settings → Calendar shows the prompt).

`MeetingEvent` is the unified model. **Never leak `EKEvent` or Graph JSON above the provider boundary.** Fields: `id, title, startDate, endDate, calendarName, location?, isAllDay, url?, notes?, attendeeNames, attendeeCount, organizerName?, isCancelled`. The provider boundary HTML-strips Graph `body.content` to plain text once, runs `ConferenceLinkExtractor.bestURL(...)` to pick the join link, and applies `CancellationTitlePrefix.matches(...)` as a fallback for cancellations whose calendar source rewrites the title to `Canceled: ...` / `Cancelled: ...` but doesn't set the structured status flag (common with older Exchange forwarding).

**Three call sites** construct `MeetingEvent`: `EventKitProvider`, `GraphCalendarProvider`, and the `Test Countdown Overlay` preview in `SettingsView`. When you add a field, update all three.

`CalendarManager` (@MainActor) polls every 30s and also subscribes to `EKEventStoreChanged` (**debounced 2s** via `scheduleChangeDrivenRefresh`, v2.19.2 — every mirror commit and every edit in Calendar.app posts one, and each used to trigger an immediate full fetch plus a reminder fan-out plus another mirror reconcile; measured 62 refreshes landing under 25s after the previous one against a 30s cadence. The debounce keeps the property the observer exists for: granting access still refreshes within ~2s, no restart) so granting calendar access in System Settings triggers a refresh without an app restart. `errorMessage` is cleared at the top of `refreshEvents()` and re-set only if a new error occurs — so stale "access denied" messages clear automatically once the user grants access.

### Countdown triggering

`CalendarManager.evaluateCountdownTrigger()` keeps two rules:

1. **De-duplication**: `triggeredCombinations: Set<String>` keyed `"\(meetingID)_\(minutes)"`. Without this, every 30s poll would re-fire. Same key pattern for new trigger logic.
2. **Policy hook**: the `shouldFireOverlay: ((CountdownTrigger) -> Bool)?` closure is consulted before setting `shouldShowCountdown = true`. `AppLifecycleManager` injects a closure that consults `ReminderEscalationPolicy`. Default (closure nil) is to respect `trigger.showOverlay` directly.

**Freshness gate + wake-aware reminders (v2.5.2):** a reminder normally only fires if its threshold was crossed within the last poll cycle (`secondsSinceCrossed <= 60`). This exists because the 30s poll timer is suspended during sleep — without the gate, waking would dump every backed-up threshold ("15 min before", "10 min before", …) for every meeting whose window passed while asleep. But the gate alone *also* drops a reminder for a meeting that's still upcoming on wake (its threshold crossed during sleep > 60s ago). The fix: `CalendarManager.refreshEvents` detects a **catch-up poll** (gap > 90s since the previous poll = the Mac was asleep) and sets `lastPollWasCatchUp`. `catchUpThresholdMinutes(for:)` returns the *single most-imminent* enabled threshold a still-upcoming meeting has already crossed. On a catch-up poll, both the overlay gate (`evaluateCountdownTrigger`) and the notification/voice fan-out (`AppLifecycleManager.observe`) additionally fire that one threshold — collapsed to one so a wake shows the relevant reminder without the backed-up stack. Normal polls are unchanged. A `NSWorkspace.didWakeNotification` observer in `CalendarManager` also forces an immediate refresh on wake instead of waiting up to 30s. **Fan-out fires once per (meeting, threshold, occurrence) — v2.19.2.** `AppLifecycleManager.firedReminderKeys` gates the notification/voice fan-out, which runs on *every* `$upcomingMeetings` publish while the 60s freshness window stays open. Without it the same reminder re-ran ~10× per threshold (observed 2026-08-27: "Reminder 15m fired" logged 10 times for one meeting); only `NotificationManager`'s dedup kept that from being 10 banners, while the **log — the first thing read when a user reports a missed reminder — overstated reality 10×** and `decide()`/rule-matching re-ran each time. The key includes `startDate`, so a recurring series whose occurrences share one EventKit id doesn't have its next occurrence swallowed. Pruned each cycle against live meeting ids. **Both gate sites must stay in sync** — they share `catchUpThresholdMinutes`; changing one without the other re-splits overlay vs. notification/voice behavior on wake.

`CountdownConfigManager.triggers` is the source of truth for which thresholds are enabled and which channels each fires; auto-persists to UserDefaults via `didSet`.

**Auto-join — "Start at Time" (v2.7.4, redesigned v2.7.5, Issue #2):** the countdown overlay has a third action beside Dismiss/Join. "Start at Time" *arms* the meeting (`CalendarManager.armAutoJoin(id)`); the meeting then collapses to a **live countdown in the menu bar** (`MenuBarExtra` label) and opens the conference link automatically when it starts. State is **keyed by meeting ID only** (`armedAutoJoinIDs` published+persisted, `joinedAutoJoinIDs` de-dup+persisted) so a reschedule/link-change is tracked from the live event, and a relaunch shortly before start still honors the arm. `evaluateAutoJoin()` (internal, **deliberately separate** from the v2.3.3 negative-countdown path) is driven by **both** the 30s poll **and** a 1-second menu-bar ticker — the poll alone would open the link up to ~30s after the displayed `0:00`, which reads as broken. It's idempotent + de-duped, so per-second calls are safe.

The v2.7.5 redesign fixed two reported bugs: (a) **arming now suppresses every original-start-time reminder for that event** — the armed-ID check is added to *both* `evaluateCountdownTrigger`'s where-clause (overlay) and the `$upcomingMeetings` notification/voice fan-out, so the menu-bar countdown is the single surface (before, later thresholds for the same meeting still fired overlays); (b) **the tap is acknowledged** — `CountdownOverlayView` shows an "Armed ✓ — counting down in the menu bar" confirmation that also covers the other buttons (so a stray Dismiss can't race the arm) for ~1.4s before arming+dismissing.

`MenuBarCountdownModel` owns the ticker: it subscribes to `$armedAutoJoinIDs` and runs a 1s `Timer` (`.common` mode) **only while something is armed** (stops when the set empties — no idle wakeups). Each tick calls `evaluateAutoJoin()` (opens+disarms due meetings) then updates the countdown UI. **The countdown lives in a dedicated `NSStatusItem` the model creates/removes itself (v2.7.7), NOT the `MenuBarExtra` label** — a separate status item is what makes **true click-to-cancel** possible (clicking a `MenuBarExtra` opens its menu instead; and a `Label` there renders icon-only so the time string wouldn't even show). The item's `button.title` is the `m:ss`/`Hh Mm` countdown and `button.toolTip` names the meeting + "click for options". **Click opens a menu, NOT an instant cancel (Issue #6, v2.9.7):** the status item's `menu` is an `NSMenu` whose `delegate` (the model, now an `NSObject` so it can conform to `NSMenuDelegate`) rebuilds it on `menuNeedsUpdate` — header (title + live countdown), **Join Now** (`joinNowAndDisarm`), **Cancel Auto-join** (`disarmAutoJoin`). A bare click used to disarm directly, which silently lost the arm when the user clicked just to show someone — don't reintroduce the direct `button.action` disarm. The `MenuBarExtra` label stays the plain app icon (red while recording). **Gentle pre-start overlay (v2.7.7):** the model also publishes `imminentMeeting` (the soonest armed meeting once `remaining <= autoJoinOverlayLeadSeconds`, default 60, when `autoJoinImminentOverlayEnabled`); a subscriber in `observe()` shows/hides `OverlayWindowController.showAutoJoinImminent` — a small non-blocking corner panel (`AutoJoinImminentView`) with a live countdown + **Join now** (`joinNowAndDisarm`) / **Cancel** (`disarmAutoJoin`). **Audible heads-up (Issue #8, v2.9.7):** when that same subscriber shows the overlay it also plays `MenuBarCountdownModel.playHeadsUpChime()` — three short beeps so a heads-down user gets a beat to stop typing before the call opens — gated on `CountdownConfigManager.autoJoinAudibleCountdownEnabled` (default on; Settings → Countdown → "Play a beep with the heads-up", under the heads-up toggle). Coupled to the heads-up: no `imminentMeeting` is published when the overlay is disabled, so no beep either. It auto-dismisses when the meeting opens (armed set empties → ticker stops → `imminentMeeting` nil). Guardrails (core alerting path — keep them): (1) **freshness bound** — open only if `now <= startDate + autoJoinGraceMinutes` (config, default 2, clamped ≥1); past that (e.g. slept through the start) it's **missed** (notify, don't open) — time-based so it covers the wake path uniformly; (2) **cancelled** → disarmed, never opened; (3) **no link** → disarmed; (4) **de-dup** via `joinedAutoJoinIDs`; (5) `armAutoJoin` only arms IDs present in `upcomingMeetings` (the Settings "Test Countdown Overlay" synthetic event can't persist a phantom arm). Auto-join fires **regardless of smart-context suppression** (explicit user intent) but is **never silent** — `onAutoJoinArmed/Fired/Missed` closures (wired in `observe()`) post `NotificationManager.sendAutoJoin{Armed,Fired,Missed}Notification`. The menu-bar dropdown also shows an "Auto-join armed — click to cancel" section (`armedAutoJoinMeetings`) to **disarm** (which re-enables normal reminders for that event). `pruneAutoJoinState` keeps both sets bounded (conservative: only drops an armed ID that's present-and-ended, never one transiently absent from a fetch). Settings → Countdown → "Start at Time (auto-join)" exposes the enable toggle + grace stepper (both gated on the Join button being on). **Known limitation:** if the app is quit through the start time, nothing fires (it's a background agent; persistence only covers a relaunch *before* start).

**Menu-bar dropdown — `.window` popover (v2.9.0, the redesign):** the dropdown is **no longer a native NSMenu**. `MenuBarExtra` uses **`.window` style** with a SwiftUI content view, selectable via `MenuBarPresentation` (Settings → Menu Bar → "Dropdown Style"): **`CompactMenuView`** (default — a menu-styled list: update/recording/cancelled/armed sections, today's meetings with inline RSVP + Join, an Upcoming popup, action rows via `SettingsLink`) or **`PopoverRootView`** (rich, CodexBar-style: Today/Upcoming segmented switcher, `DayTimelineBar` hero + "NEXT · in 12m" band, callout cards [Recording=red / Auto-join=accent / Update=accent / Cancelled=orange], columned event rows, day pager; hero/cards/timeline live-tick via a single 1s `TimelineView`). **Why both are SwiftUI under `.window` (do not re-litigate):** `MenuBarExtra` can't switch `.menu`/`.window` at runtime (SceneBuilder rejects *any* conditional around scenes — even a single `if`), AND a hand-built AppKit `NSMenu` can't reliably open the SwiftUI `Settings` scene (the v2.7.1 `showSettingsWindow:` failure; `SettingsLink` is SwiftUI-only). So dropping `MenuBarExtra` for a hand-built `NSMenu` was abandoned; both presentations are SwiftUI views in one `.window` `MenuBarExtra`. The true native menu is retired. Full design + rollout history: `docs/popover-redesign-spec.md`. **Data:** `refreshEvents` does **one** wider fetch (`upcomingDaysAhead`, default 7) **filtered back** to the reminder window for `upcomingMeetings` — reminder/cancellation/auto-join paths are byte-for-byte unchanged; `upcomingWeek` / `events(on:)` / `upcomingDaySchedules()` feed the browser. `CalendarManager.lastRefreshDate` (success-only) backs the popover header's "synced Xm ago". `observe()` runs from the always-present label `.onAppear`, **idempotent** (`hasObserved`). **Fit-to-content height (v2.19.0, opt-in `@AppStorage("popoverFitToContent")`, default off, Settings → Menu Bar).** With it on, each list (Today/Upcoming **and** Tasks) is sized to its **measured** rows rather than a reserved block: a `GeometryReader` + `PreferenceKey` reports content height, and `ListSizing` sets an explicit `.frame(height: clamp(measured, 44, cap))` where `cap = 70% of the visible screen − popoverChromeHeight (350: header/timeline/NEXT band/footer)`. The fitted height is **snapped to whole rows** (`fittedHeight(_:rowCount:)`), deriving row height from the measurement itself — `(measured − 4pt padding) / rowCount` — rather than a constant, so the bottom edge lands *between* rows instead of slicing one against the footer. On the legacy path the parent decides the height, so snapping isn't possible; it gets a **bottom fade mask** instead (`bottomFade`, applied at ≥5 rows), which is purely visual — **no measurement on that path**, since measuring there is precisely what caused the v2.19.0 scroll jank. Scroll indicators appear **only** when `measured > cap`. Measured on a 1169pt screen: one meeting shrinks the list from the 300pt block to 44pt; fourteen meetings grow it to 468pt instead of scrolling at 300. **The two modes are separate view trees, deliberately** (v2.19.1): measuring in both — a `GeometryReader` background feeding `@State` — wrote state on *every layout pass*, so with the toggle **off** the legacy path picked up a re-render per scroll frame and felt janky. Off must mean the original view tree, untouched; don't refactor the branches back together. The preference handler also ignores sub-0.5pt changes. **Measuring is also what keeps the v2.9.4 bug dead** — an explicit height can't be squeezed to ~0 the way a flexible frame could. Legacy path (toggle off) keeps the exact `minHeight/maxHeight` frames below.

**Height-clipping guard (v2.9.4):** the event-list `ScrollView` has `minHeight: 140` so the `.window` popover (which sizes to content) can't squeeze the flexible list to ~0 on a shorter display — the symptom was a populated hero/timeline but an **empty event list on one device** while another showed it. `PopoverRootView.onAppear` logs version + screen height + today/shown counts to triage device-to-device differences. **Retired in v2.9.0:** `MenuBarView` (native menu), `UpcomingDaysPanelView`/`UpcomingPanelController` (the v2.8.0 floating panel), and `UpcomingHeaderStyle` (v2.8.4 — only the native submenu used it).

**Menu Bar settings tab (`SettingsSection.menuBar`, slimmed v2.9.2):** Dropdown Style (`MenuBarPresentation`: menu | popover, **default popover**), **Upcoming Days** (`upcomingDaysAhead` stepper — the fetch/pager horizon, used by both modes), **Accent Color** (`nextMeetingHighlightHex` — the highlight used throughout). **v2.9.2 retired** the now-vestigial `UpcomingViewStyle` (off/submenu/perDay/popover) and `UpcomingDayLabelFormat` (+ show-count) settings: they were leftovers from the native-menu submenus and had **no effect in the default popover** (which has its own Today/Upcoming switcher); the compact menu now shows a fixed-format Upcoming popup (`UpcomingDayFormat.header` · count). Every remaining control affects both presentations.

**Meeting-start notification (v2.7.6):** a system notification at T-0, in addition to the pre-meeting countdown reminders. A `$meetingsCurrentlyRunning` subscription in `observe()` fires `NotificationManager.sendMeetingStartedNotification` for each newly-running meeting **within a 120s freshness window** (`meetingStartNotifyWindow`) — so launch/wake, where `meetingsCurrentlyRunning` surfaces meetings already long in progress, doesn't announce a stale start. Per-ID dedup (`started_<id>`) keeps it to once. **Skipped** for armed auto-join meetings (their auto-join posts its own "Joining" notice) and RSVP-suppressed ones; `meetingsCurrentlyRunning` already excludes cancelled. Toggle: `NotificationManager.notifyAtStartEnabled` (default on), Settings → Countdown → "Meeting Start".

### Cancellation handling (v2.2.0)

Cancelled meetings are first-class: notify once on detection, suppress all original-start-time channels (overlay, notification, voice, auto-record).

- **Detection** lives in the providers (`EKEvent.status == .canceled` / Graph `isCancelled`, with `CancellationTitlePrefix` as fallback). The flag rides through on `MeetingEvent.isCancelled` so downstream code never has to ask the calendar source again.
- **`CalendarManager` owns the persistence**: `notifiedCancellationIDs` (we've already fired the notification) and `dismissedCancellationIDs` (user clicked Dismiss on the dropdown badge). Both persist to UserDefaults so an overnight cancellation is still visible in the dropdown the next morning — Jon's "someone in Japan cancelled while I was asleep" case. `pruneCancellationState` drops IDs whose corresponding meeting has ended, keeping the sets bounded.
- **Fan-out** is in `AppLifecycleManager.observe`: a dedicated `$upcomingMeetings.sink` runs **before** the regular reminder fan-out, so a freshly-cancelled meeting in the same refresh cycle never fires both a cancellation notification AND a stale reminder. Each cancelled meeting matched against `notifiedCancellationIDs` → either notify + mark, or skip.
- **"Why no reminder?" diagnostic (v2.9.6):** the suppression gates are otherwise silent, so a meeting that won't fire (cancelled / RSVP-declined / armed-for-auto-join) left no trail. `evaluateCountdownTrigger` now logs **once per meeting** (`loggedReminderSuppressions`) why an in-window meeting won't fire — e.g. "No reminder will fire for "…" — marked CANCELLED …". This is the triage line for "my overlay didn't show." (Real case: an EventKit event with `status == .canceled` correctly suppressed its overlay+notification; the log makes that visible instead of looking broken. Note `CancellationTitlePrefix.matches` is **prefix-only** — `hasPrefix("canceled:"/"cancelled:")` — so "cancel" mid-title does NOT flag it.)
- **Suppression** is symmetric across every reminder channel: `CalendarManager.evaluateCountdownTrigger`'s outer `where` adds `!event.isCancelled`; `AppLifecycleManager`'s reminder fan-out adds the same gate; `MeetingRecordingCoordinator.shouldRecord` adds `&& !meeting.isCancelled`. Cancelled meetings are still added to `todaysMeetings` (the menu bar shows them struck-through) and to `meetingsCurrentlyRunning` excludes them so the handoff coordinator doesn't switch audio for a meeting that isn't happening.
- **Today view in `MenuBarView`**: replaces the old "Next Meeting" header. Renders `todaysMeetings` as compact rows, cancelled ones get `.strikethrough()` + a red `xmark.circle.fill`. Above the list, when `pendingCancellations` is non-empty, a "Cancelled Today" section shows each one as a clickable menu Button that dismisses it via `calendarManager.dismissCancellation(id)`. Display capped at 8 rows + "+N more" overflow. **NSMenu rendering constraint**: `MenuBarExtra(.menu)` flattens SwiftUI containers — an `HStack` of `Text`s becomes one menu item *per Text*, splitting rows across lines. Every meeting row is therefore built as ONE concatenated `Text` (`meetingRowText(for:)`: time + title + status glyph via `Text + Text`), which is the only reliable way to get a styled single-line row inside NSMenu. `textCase`/`tracking`/`padding` modifiers return `some View` (not `Text`) and re-trigger the splitting — avoid them in menu content.
- **User settings (v2.2.6–v2.2.7)** in the Countdown tab's "Cancelled Meetings" section: `cancellationNotifyEnabled` + `cancellationPlaySound` (on `NotificationManager`, default on), `cancellationShowInTodayView` (@AppStorage, default on, display-side filter only), `cancellationShowOverlay` (@AppStorage, **default off**), `cancellationOverlayPosition` (@AppStorage `String` wrapping `OverlayWindowController.CancellationOverlayPosition` rawValue, default `topRight`; `.topRight` anchors the panel to the top-right corner of the screen, `.center` places it at the screen midpoint — picker is disabled while `cancellationShowOverlay` is off). The fan-out in `AppLifecycleManager` always calls `markCancellationNotified` even when notify is off — "notified" means "seen", which the badge and dedup depend on. Suppression of original-start-time reminders is hardcoded, deliberately not a setting.
- **Cancellation notice is a persistent acknowledgment surface, NOT a toast (v2.3.2).** `CancellationOverlayView` renders the persisted `pendingCancellations` list (each row has its own Dismiss); **no auto-dismiss timer** — the original 12s toast self-expired before anyone saw it (and `Task.sleep` counts wall-clock time through system sleep, so a notice shown pre-lid-close was already dead at wake). Display is **state-driven**: a `CombineLatest($pendingCancellations, $snapshot)` subscriber in `AppLifecycleManager` shows/hides `OverlayWindowController.showCancellationCenter(_:onDismissItem:)` (idempotent on the pending ID set). Overnight cancellations are on screen at lid-open and survive restarts until acknowledged. Overlay Dismiss calls the same `dismissCancellation(id)` as the dropdown badge — one acknowledgment system. **Smart-context hold**: hidden while in a call (gated on `suppressWhenInCall`) or screen-sharing; reappears automatically when the hold clears.
- **Both overlay panels force `NSAppearance(named: .darkAqua)` (v2.3.2)** — they're dark-designed (hardcoded white text on `.hudWindow` blur), and that material follows system appearance: without the forced appearance, light mode renders it light and the white text is invisible. Any new always-on-top panel with the dark design must set this (the QuickAdd panel achieves the same via `.colorScheme(.dark)`).

### Meeting time-change detection (Issue #5, v2.9.7)

When an existing meeting's **start time moves**, notify once ("Meeting moved — now X, was Y") so you don't get dressed and sit down for a meeting that's been rescheduled (Queensly's case). Same family as cancellation handling — autonomous, state-in-the-calendar-diffed-against-persisted-state.

- **`CalendarManager.detectTimeChanges(in:)`** runs each poll over the **wider `allEvents` browse window** (so a move a few days out is caught, not just inside the reminder window). It compares each still-upcoming event's `startDate` against `knownStartTimes[id]` (persisted JSON, `[String: Date]`); a difference ≥ `timeChangeMinDelta` (60s, hardcoded — ignores sub-minute jitter) fires `onMeetingTimeChanged(event, priorStart)` (wired in `observe()` → `NotificationManager.sendTimeChangeNotification`). Baselines refresh every poll.
- **First-sight never notifies** — a meeting with no prior baseline only records one. This is the key false-positive guard: on first launch after upgrade every event is first-sight, so the upgrade itself is silent.
- **Recurring events are keyed by occurrence, not skipped (v2.15.3).** EventKit gives *every occurrence the same `eventIdentifier`*, so an id-keyed baseline would fire a false "moved 24h" as each occurrence rolls over across the 7-day window — the reason the original v2.9.7 code skipped recurring events entirely (missing a reported real reschedule of a weekly sync). The fix: baseline recurring events by **`id + occurrenceDate`** (`MeetingEvent.occurrenceDate` ← EventKit `EKEvent.occurrenceDate`), the occurrence's *original* slot, which stays fixed even when the occurrence is moved. So each occurrence is tracked independently (no rollover false positives) AND a moved occurrence is detected (its `startDate` diverges from the baseline). `detectTimeChanges` builds `baselineKey = "id\u{1F}occEpoch"` for recurring, bare `id` otherwise; `pruneTimeChangeState` recovers the id from either form (bare id, or prefix before `\u{1F}`). A recurring event with **no** `occurrenceDate` (the Graph provider doesn't expose it) is still skipped — Graph recurring reschedules remain a gap. `isRecurring` is set at the provider boundary — EventKit `event.hasRecurrenceRules`; Graph `type != "singleInstance"`. (`occurrenceDate` defaults nil; only the EventKit site sets it — Graph + the SettingsView test preview leave it nil, both correct.)
- **Dedup** keyed `"<id>_<newStartEpoch>"` (`notifiedTimeChanges`, persisted) so a move notifies once even across relaunch. **Pruning** (`pruneTimeChangeState`) drops baselines/keys for events outside the fetch window; safe because a transiently-absent-then-reappearing event becomes first-sight (worst case a missed notice, never a false one).
- **Armed auto-joins re-anchor automatically** (keyed by ID, re-read the live `startDate`), so a moved armed meeting still opens at the new time — the notification is purely the heads-up. All-day + cancelled events are skipped (cancellation has its own channel). Toggle: `NotificationManager.timeChangeNotifyEnabled` (default on), Settings → Countdown → "Rescheduled Meetings".

### Smart context detection (`MeetingContext/`)

Four detectors + monitor + pure-function policy:
- **`FrontmostAppDetector`** — `NSWorkspace.didActivateApplicationNotification` push-driven. Bundle ID match against a video-conf allowlist; fullscreen check via `CGWindowListCopyWindowInfo` window-bounds.
- **`MicrophoneDetector`** — CoreAudio `kAudioDevicePropertyDeviceIsRunningSomewhere` listeners on each input device. **No mic prompt** because we never open the device for capture.
- **`FocusModeDetector`** — `INFocusStatusCenter` (read-only API). Polls every 10s; `.denied` is treated as "Focus off." Requires `NSFocusStatusUsageDescription` in `project.yml`.
- **`ScreenCaptureDetector`** — heuristic: known-recorder bundle ID running OR (conference app frontmost AND mic in use). **No public macOS API exposes "is being captured by another process"** — `CGDisplayIsCaptured` is deprecated on macOS 14+, `SCShareableContent` only lists shareable resources, not capture state. The heuristic is the best we can do without Screen Recording permission. The detector takes closures for frontmost-bundle-ID and mic-in-use so it stays decoupled; `MeetingContextMonitor` wires them and pokes `refresh()` on every input change.

**`CameraUseDetector`** (`MeetingContext/`, v2.18.0) — the CoreMediaIO twin of `MicrophoneDetector`: `kCMIODevicePropertyDeviceIsRunningSomewhere` instead of the CoreAudio selector, listeners on every camera device (built-in, Desk View, Continuity, externals — **OR across all of them**), plus a `kCMIOHardwarePropertyDevices` listener so a plugged-in webcam is picked up. **It never opens a device**, so there's no camera permission prompt, no green LED, and no menu-bar dot — verified on an M5 MacBook Pro (macOS 26.1) where it caught FaceTime starting/stopping. **Subscribe, don't poll:** a cold one-shot read from a process with no listener registered was observed returning stale `false` while the camera was live, so state is kept from callbacks and never re-derived by a bare read elsewhere. It is deliberately NOT part of `MeetingContextSnapshot` — nothing in the reminder policy consults it.

### Camera cover reminder (`CameraCoverReminder.swift`, v2.18.0)

Opt-in (**off by default**, Settings → Plugins → Camera Cover): a nudge to close a physical camera flap once you're out of meetings, with its own distinct sound.

- **It cannot see the cover, and must never pretend to.** No API exposes a piece of plastic; checking by capturing a frame would need camera permission and would light the green LED on every check (the LED is hardware-interlocked to the sensor — Apple guarantees it can't be bypassed). So the copy is conditional — *"Close camera flap if open"* — never "your camera is exposed". **Don't "improve" that wording into a claim.**
- **Two triggers:** a scheduled meeting ended (set-diff on `$meetingsCurrentlyRunning`, the handoff-coordinator pattern), or the camera stopped streaming (`CameraUseDetector`, which catches the off-calendar call — where a cover actually gets forgotten).
- **Conditions are re-tested at FIRE time, not schedule time** (`delayMinutes` later, default 2): no meeting running, camera not in use, and the next meeting not within `skipIfNextMeetingWithinMinutes` (default 10). Everything relevant can change during the delay.
- **A blocked check retries, it isn't dropped** (v2.19.2): "a meeting is running" and "the camera is in use" are transient, so `retry(...)` re-arms every 2 min up to 5 attempts (~10 min). Observed 2026-08-27: three consecutive checks were skipped and the nudge only landed because an unrelated trigger fell in a free moment — on a back-to-back day that's no nudge at all. "Next meeting is close" still drops, since that meeting's end schedules a fresh check anyway.
- **One nudge per event, never a repeat** (`handledKeys`) — a reminder that nags twice gets switched off, and then it protects you never.
- **Its own sound:** `NotificationManager.sendCameraCoverNotification` sets `content.sound = nil` and plays `/System/Library/Sounds/Pop.aiff` itself, so the banner can't double up with the default alert; different meaning, different noise. Falls back to `NSSound.beep()` if the file is ever missing.
- **Rotating wordings** (`CameraCoverMessage.templates`): six phrasings, never the same one twice in a row (`lastMessageIndex`). Every one **asks** ("Is your meeting over? · If so, close your camera cover.") — don't add a variant that asserts the camera is uncovered, because we don't know. Rotation matters more here than for meeting reminders: it's the same message forever, and identical text becomes wallpaper.
- **Do Not Disturb switches surface, it doesn't silence** (v2.18.1, `CameraCoverConfig.notifyDuringFocus`, default **on**). macOS holds notification banners during Focus, and the sanctioned way through — `interruptionLevel = .timeSensitive` — needs a restricted entitlement (provisioning-profile territory for a Developer ID build) and is downgraded **silently** when unauthorized, so you'd ship a promise you couldn't verify. Instead: Focus on → `OverlayWindowController.showCameraCover`, an `NSPanel`, which Focus doesn't govern; Focus off → the notification. With the toggle off it stays silent, sound included. The panel auto-closes after 10 min (`cameraCoverMaxMinutes`) so it can't become the hours-long zombie the countdown overlay was before v2.15.2. **`Test` goes through the same surface selection**, so testing under Focus shows exactly what Focus will get — the earlier version played the sound with no banner and read as broken, which cost a debugging round trip.
- **The sound is played by the app** (`playCameraCoverSound`, now internal so the panel path can use it), not carried on the notification — that's what allows a distinct sound without bundling an audio asset, and it's why the Focus handling above has to be explicit rather than delegated to macOS.
- **No new entitlement or usage string** — that's the point of the property-read approach.

`MeetingContextMonitor` aggregates into `MeetingContextSnapshot`. `ReminderEscalationPolicy.decide(trigger, context, config)` is pure: evaluates rules top-to-bottom (most aggressive first: in-call → suppress-all; Focus on → visual-only; sharing → no voice; fullscreen → escalate), returns `ReminderDecision`. `SmartConfigManager` persists the four user toggles individually.

**In-call definition — open conference app alone is NOT "in a call" (v2.7.3).** `MeetingContextSnapshot.isInActiveCall` is `isMicrophoneInUseElsewhere` only — a frontmost/open Zoom/Teams window no longer asserts in-call on its own. Rationale: real calls keep the mic device "running" (`kAudioDevicePropertyDeviceIsRunningSomewhere` stays true even when muted), so genuine calls still detect; an idle conference app left open all day does not. **This is the fix for the v2.7.0 regression** where `isInActiveCall = conferenceAppActive || micInUse` latched true for ~11.5h off a single forgotten Teams window, silently muting every reminder (`suppressAll`) and holding the cancellation notice all day with zero WARN. `isConferenceAppActive` survives as a `MeetingContextSnapshot` field / Live-Signals detail but no longer drives suppression. **Don't reintroduce the OR.** Three additional guardrails live in `AppLifecycleManager.observe`'s cancellation-overlay subscriber: (1) **safety valve** — a held cancellation notice surfaces anyway after 30 min (`cancellationHoldMaxInterval`; `Date()` comparison spans system sleep, so an overnight hold is past the bound by lid-open); (2) **transition-only logging** — the "Cancellation overlay held" line logs on hold engage/clear, not every snapshot tick (it was 82% of one day's log); (3) **stuck-suppression WARN** — `trackInCallSuppression` emits one `.reminder` WARN naming the asserting signal once continuous in-call suppression passes 90 min (`stuckSuppressionWarnInterval`), making an abnormally long all-channel mute greppable.

**In-call mute — diagnosable, visible, self-healing (v2.10.0).** A user reported the app "stopped working"; the July-1 log showed 100% continuous polling but the one due reminder fired `notify=false voice=false overlay=false` — the mic was detected in use and `suppressAll` silently muted it, with no visibility. Four fixes closed the gap:
- **Reason logging** — `ReminderDecision` carries `suppressedBy: ReminderSuppression?` (`.inCall`/`.focus`/`.screenSharing`), set per `decide` branch; the fan-out log appends ` — suppressed: <reason>`. A silent mute is no longer a black box (this is now the first thing to grep for a "no reminder fired" report).
- **Visible indicator** — the muted predicate is `smartConfig.suppressWhenInCall && contextMonitor.snapshot.isInActiveCall`. The `MenuBarExtra` label shows `bell.slash.fill` ("Reminders paused") — a third branch after recording — and both dropdowns (`CompactMenuView` status row, `PopoverRootView` informational `calloutCard`, also OR'd into `showSectionDivider`) show "Reminders paused — you're on a call." Both dropdown views now receive `smartConfig` + `contextMonitor` (threaded from `menuContent`). A Live-Signals "Reminders muted" row mirrors it in Settings.
- **Auto-release cap** — `SmartConfigManager.maxInCallSuppressionMinutes` (default **30**, `0` = never). `trackInCallSuppression` (now also passed `config`) sets `inCallSuppressionCapExceeded` once the continuous episode passes the cap + WARNs once; the `decide` closure (`[weak self]`) overrides only the `.inCall` decision to `.fromTrigger` so reminders resume even while the mic stays held — a stuck mic can't mute forever. When the cap is `0`, the legacy 90-min WARN-only path is retained. Recording is unaffected (not driven by `decide`); Focus/screen-sharing suppression is untouched (guarded on `== .inCall`). Setting: Smart → "Auto-resume reminders after N min on a call."
- **Opt-in notification during a call (Issue #12)** — `SmartConfigManager.inCallStillNotify` (default **off**). When on, the in-call branch returns `sendNotification: trigger.sendNotification` (overlay + voice still off) instead of `.suppressAll` — so you get a quiet heads-up on a call without the intrusive overlay. `suppressedBy` stays `.inCall`, so the auto-release cap still applies. Setting: Smart → "…but still send a notification."

**Per-event notification rules (v2.10.1).** User-defined rules that pick which channels fire for meetings they match — e.g. a "Focus Time" rule that allows only the system notification. `NotificationRule` (Codable: `name`, `enabled`, `titlePattern`, `condition: RuleCondition {anyMeeting/organizedByMe/justMe}`, + the three channel flags `showOverlay`/`sendNotification`/`playVoice` — same vocabulary as `CountdownTrigger`/`ReminderDecision`) lives in `ReminderEscalationPolicy.swift`; `NotificationRule.matches(_:)` does the title match (case-insensitive **contains**, auto-upgrading to `NSRegularExpression` when the pattern has regex metacharacters — `looksLikeRegex`) AND the condition (`organizedByMe` = `myResponse == .organizer` reliable; `justMe` = `attendeeCount <= 1` **approximate** — the app stores no current-user identity). Rules persist as JSON on `SmartConfigManager.reminderRules` (key `smart_reminderRules`) with `addRule`/`removeRule`/`updateRule`; `channelMask(for:)` returns the first enabled matching rule's flags. **Integration is downgrade-only at the single decision point:** the `decide` closure (widened to `(CountdownTrigger, MeetingEvent)`) `&&`s the mask onto the policy decision — so it can silence channels but never enable ones the threshold didn't request (consistent with the policy contract). `CalendarManager.shouldFireOverlay` was widened to `(CountdownTrigger, MeetingEvent) -> Bool` to thread the event to the overlay gate; the notify/voice fan-out passes `meeting` too and appends `— rule: <name>` to the reminder log. UI: Settings → Smart → "Notification Rules" (list + `RuleEditSheet`, mirrors the Quick Add Templates editor).

**Steady menu-bar icon — green-on-update is the ONLY allowed change (v2.15.2).** By explicit user request (2026-07-27: "I keep losing it because the icon changes"), `menuBarLabel` is now a **steady plain `clock`** that does NOT swap for recording or reminders-paused. The **only** state that changes it is an available update → `clock.badge.checkmark` with `.symbolRenderingMode(.palette).foregroundStyle(.primary, .green)` (a green checkmark badge). So `menuBarLabel` has exactly two branches: `isUpdateAvailable` (green check) → else plain clock. The recording (`record.circle.fill`) and muted (`bell.slash.fill`) branches — and the now-dead `remindersMutedByCall` helper — were removed; recording/muted still surface in the dropdowns + notifications, just not on the icon. **Do NOT reintroduce a recording/muted/overdue glyph swap** (see the `flag-menubar-icon-changes` memory + the Tasks-section note). **Caveat unchanged:** the menu bar may template the icon monochrome and strip the green; fallback is a non-template `NSImage` if needed.

### RSVP / response gate (v2.6.1) + in-app RSVP write (v2.7.0)

**Writing the response (v2.7.0, Graph-only):** `CalendarProvider` gained `supportsResponding: Bool` + `respond(to:status:)`. `GraphCalendarProvider.respond` POSTs `/me/events/{id}/{accept|decline|tentativelyAccept}` with `{"sendResponse": true}` — **accepts HTTP 200/202/204** (accept returns 202; routing it through the read path's 200-only check would wrongly fail). `EventKitProvider.respond` throws `.notSupported` (`supportsResponding=false`) — **Apple provides no EventKit API to RSVP**, same family as can't-add-attendees, so this is Graph-only by necessity. `CalendarManager.respond(to:status:)` delegates + refreshes + logs to Diagnostics; `supportsRSVPWrite` exposes the capability. UI: in the menu-bar dropdown, an **invitation** (active provider write-capable AND `myResponse ∈ {accepted,declined,tentative,noResponse}` — not organizer/unknown) renders its `meetingRowText` as the **label of a `Menu`** (native NSMenu submenu) with Accept/Tentative/Decline, checkmarked on the current response. The full click-toggle UI is deferred to the **v2.8.0 popover redesign** (`.menu`→`.window`). NSMenu submenu is the no-redesign interim.

`MeetingEvent` carries `myResponse: ResponseStatus` (`accepted/declined/tentative/noResponse/organizer/unknown`, default `.unknown`) and `responseCounts: ResponseCounts?` (everyone's tally, for the details panel). Captured at the provider boundary: **EventKit** from the `EKParticipant` where `isCurrentUser == true` (or `.organizer` if `event.organizer?.isCurrentUser`; `.unknown` when attendees exist but none matches — multi-account edge case); **Graph** from `event.responseStatus.response` (added to the `$select` + a `GraphResponseStatus` Codable) and per-attendee `status.response`. As always, **all three `MeetingEvent` construction sites** (EventKit, Graph, SettingsView test previews) set the fields.

**Gating is a hard gate at the fan-out sites, NOT in `ReminderEscalationPolicy`** — the policy is for live OS context; RSVP is calendar state. The single source of truth is `MeetingEvent.suppressedByResponse(skipDeclined:skipNoResponse:)`, which **only ever suppresses `.declined` / `.noResponse`** — accepted/tentative/organizer/unknown always pass, so personal events and meetings you own are never silenced. `SmartConfigManager` holds two toggles: `skipDeclinedMeetings` (default **on**) + `skipNoResponseMeetings` (default **off**); its `suppresses(_:)` convenience is injected as a closure into the three gate sites in `AppLifecycleManager.observe`: `CalendarManager.responseGate` (overlay where-clause), the `$upcomingMeetings` reminder fan-out (notification/voice), and `MeetingRecordingCoordinator.responseSuppressed` (`shouldRecord`). **Keep the three in sync** — they all call the same helper; changing one without the others re-splits behavior. Every suppression logs to `DiagnosticLog` (the fan-out log is gated to the largest-threshold window so a declined all-day meeting doesn't spam every 30s). RSVP also surfaces in the Today view (a glyph for declined/tentative/no-response only) and the overlay details panel ("Your response" + the counts summary).

### Overlay window (`OverlayWindowController`)

The overlay is **not** a SwiftUI `Window` — it's an `NSPanel` wrapping `NSHostingView(CountdownOverlayView)`, with `.canJoinAllSpaces | .fullScreenAuxiliary` collection behavior and `.floating` level so it appears over fullscreen Zoom/Teams. SwiftUI's window scenes can't reliably do always-on-top + non-activating.

**Panel size fits the content and the screen (v2.15.4).** It used to be a hardcoded **720pt** (details panel showing) / **560pt** (not) at `show(for:)` time — wrong in both directions: it swallowed a 1080p display (the reported "the overlay fills my screen"), *and* on a busy meeting the content genuinely needed ~890pt, so the Join/Dismiss buttons fell off the bottom of the panel. Now:
- **Compact layout** (`CountdownOverlayView.compact`) when the screen's visible height is under `compactBelowScreenHeight` (1100pt — covers 1080p and most laptops) or when the user forces it via `CountdownConfig.overlayCompactLayout` (Settings → Countdown → "Always use the compact overlay"). Compact scales the ring/type/spacing down; **every metric that differs lives in the "Layout metrics" block** at the top of the view — keep new ones there so the two layouts stay in proportion. The controller picks `compact` and the view is handed the same flag, so the panel and its content always agree.
- **Height comes from `CountdownOverlayView.contentFittingHeight(width:)`** (a throwaway `NSHostingView` probe over the non-scrolling `content`), clamped to `minPanelHeight` (360) … `maxScreenFraction` (0.72) of the visible frame. No magic 560/720 anywhere.
- **The view is header + scrolling `infoSection` + pinned `actionSection`.** Only the middle (title/ring/details/start-time) scrolls; Join / Start at Time / Dismiss are outside the scroll area, so however hard the screen clamp bites, the overlay always shows its actions. **Don't put the actions back inside the scroll area** — that's the regression this structure exists to prevent. `MeetingDetailsPanel` takes the same `compact` flag (tighter padding + shorter notes box).

Calling `show(for:)` while a panel exists is a no-op (`guard overlayWindow == nil`).

**Simultaneous meetings — four selectable styles (v2.17.0).** Meetings that start together used to produce **exactly one** overlay and the rest were silently lost: `evaluateCountdownTrigger` fired the first and `return`ed, and on the next poll the others were marked triggered *before* the `!shouldShowCountdown` check rejected them — never shown, never retried. Now the trigger loop **collects every meeting whose threshold crosses in the same poll** into `CalendarManager.countdownMeetings` (ranked by `rankedForOverlay`: accepted/organizer first, then has-link, then start, then title), and `OverlayWindowController.show(for: [MeetingEvent])` presents the group per `CountdownConfig.concurrentOverlayStyle` (`ConcurrentOverlayStyle`, default `.heroPlusStrip`):
- **`conflictPanel`** — one panel for the timeslot: shared ring + a `ConcurrentMeetingRow` per meeting (Join + ⏰ arm) + "Dismiss all" (`ConflictOverlayView`).
- **`heroPlusStrip`** — the normal single-meeting overlay for the lead, with the others in an "ALSO AT hh:mm" strip inside the **scrolling** info area (`CountdownOverlayView.alsoAtThisTime`), so the pinned actions still can't be pushed off.
- **`pager`** — one meeting at a time; header reads "MEETING 1 OF 3" and **Dismiss becomes "Next ›"** for all but the last (`pagerPosition` + `onNextInGroup`; controller keeps `groupForPager`/`pagerIndex`).
- **`cardStack`** — a compact card per meeting anchored **top-right** (clear panel background, cards draw their own chrome); dismissing one re-presents the remainder, the last one closes the panel (`ConflictCardStackView`, `cardStackMeetings`).
**Notifications + voice collapse the same way (v2.17.0).** The `$upcomingMeetings` fan-out now **collects** what would fire (`notifyQueue`/`voiceQueue`) and dispatches after the loop, grouped by `threshold + start minute` — note this is the **start time**, deliberately not the overlay's "same poll" rule, so the banner can honestly say "3 meetings at 10:00" (9:58 and 10:00 stay separate messages). `CountdownConfig.concurrentNotificationStyle` (`ConcurrentNotificationStyle`, default `.grouped`): **grouped** = one banner via `sendGroupedCountdownNotification` (which also claims each meeting's own `"<id>_<minutes>"` dedup key, so the next poll can't follow up with the individuals it replaced); **threaded** = per-meeting banners sharing a `threadIdentifier` so macOS stacks them in Notification Center; **separate** = the pre-v2.17.0 behaviour. Voice always collapses to one line (`speakGroupReminderIfNeeded`) — three utterances used to read over each other.

**Auto-join clash (v2.17.0).** `evaluateAutoJoin` iterates armed meetings in `rankedForOverlay` order and, unless `CountdownConfig.autoJoinOpensAllOnClash` is on (default **off**), opens only the first due meeting per tick; the rest are marked joined (so they can't spring open a moment later), left unarmed, and reported once via `onAutoJoinClash` → `sendAutoJoinClashNotification` ("Opened X · 2 other meetings started at the same time"). Three browser windows at once is not a usable way to start a meeting, and the notification keeps the choice from being silent.

A **group with one meeting takes the untouched single-meeting path** in every style. Settings → Countdown → "Simultaneous Meetings" has the picker plus **Test with 3 meetings at once**, which drives the real path with three synthetic events (one accepted+link, one tentative+link, one no-response/no-link) — the clash is too rare to choose a style by waiting for one. The test fires **all three surfaces**: overlay, notification (through the same `ConcurrentNotificationStyle` switch the fan-out uses), and the spoken line — the notification/voice behaviour is exactly what a screenshot can't show. Sample ids carry a run timestamp so a second click isn't swallowed by the id-keyed dedup sets (`sentNotificationKeys`, `spokenMeetingIDs`). Joining from a group closes the whole overlay (joining is the acknowledgment); arming from a group closes only that card.

**Countdown lifecycle (v2.3.3): the overlay does NOT close at meeting start.** At 00:00 it flips to "MEETING IN PROGRESS" and counts negative in red ("since start") until the user joins (Join also dismisses — joining is the acknowledgment), dismisses, or the meeting's **end** time passes (safety net, enforced both in the view's timer and in `CalendarManager.evaluateCountdownTrigger` — the poll-side auto-dismiss checks `endDate`, not `startDate`; changing it back to start-time would silently kill the negative-countdown feature on the next 30s poll).

**In-progress auto-close cap + un-stallable dismiss (v2.15.2).** Fixes a real report: an overlay for a long evening event stayed up **~12h** and went unresponsive ("won't close or respond to any input"). Three root causes, three fixes:
1. **A long meeting (or a far-off `endDate`) pinned the overlay for its whole duration.** `CountdownConfigManager.inProgressOverlayMaxMinutes` (default **15**, `0` = legacy "until end") caps how long the post-start overlay lingers, independent of `endDate`. Enforced in **both** the poll-side (`evaluateCountdownTrigger`) and the view-side (`CountdownOverlayView` timer) auto-dismiss — keep the two in sync. Setting: Countdown → "Overlay Auto-Close".
2. **The poll-side auto-dismiss sat AFTER the trigger loop's early `return`, so it only ran on quiet polls.** It's now moved to the **top** of `evaluateCountdownTrigger` and runs every poll unconditionally — so a busy/long meeting can't skip it, and clearing `shouldShowCountdown` early frees the single overlay slot for a later meeting's reminder (previously the pinned overlay silently swallowed the next meeting's overlay). **Do not move it back below the loop.**
3. **A stalled `Timer` froze the overlay + killed its buttons.** The view timer is now created unscheduled and added via `RunLoop.main.add(t, forMode: .common)` (survives menu/event-tracking) and `OverlayWindowController.dismiss()` does `orderOut` + `contentView = nil` + `close()` so the `NSHostingView`'s `onDisappear` fires and invalidates the timer (no leaked/zombie panel). `dismiss()` also now logs `Countdown overlay dismissed` — there was previously **no** dismiss log line, which is why the triage log showed a show with no corresponding close.

**Join action is never a dead end (Issue #9, v2.9.7):** the Join button has no `hasStarted` gate — it shows whenever there's a link + `joinButtonEnabled` — so a meeting with *no detected link* (`meeting.url == nil`) left the post-start overlay with no action at all (Jon came back a minute late to a negative countdown and nothing to click). The button now opens `meeting.url ?? fallbackJoinURL`, where `fallbackJoinURL` is the first http(s) link found anywhere in the notes/location via `NSDataDetector` (label becomes "Open Meeting Link") — this catches join links from providers `ConferenceLinkExtractor` doesn't recognize (it only accepts `eventURL` when the host is a *known* provider, and only regex-scans for known patterns). When there's truly no link, the overlay shows an **Open in Calendar** button (`ical://`). This is **overlay-only** — it does NOT change reminder gating, auto-record, or the structured extractor.

**Grouped action block (v2.16.4).** The action area is one bordered group, not loose buttons: a **full-width primary bar** (green Join Meeting / Open Meeting Link, or neutral **Open in Calendar** when there's no link at all) over a **split row** whose two halves — Start at Time | Dismiss — share the border and a hairline divider; "Don't remind me again for this" stays outside it as a text link. Built from `OverlayActionCell` (a full-bleed rectangle, not a capsule, so cells can share edges with no gaps; hover lifts the fill). Replaces the old three-shapes stack (filled capsule + two outlined capsules + a link), which gave one primary and three secondary actions three competing visual tiers. Degrades correctly: no Start at Time after the meeting starts or without a link, so Dismiss takes the whole row. Also ~110pt shorter than the pre-v2.16.4 stack — it feeds straight into the content-derived panel height above.

### System handoff (`SystemHandoff/`)

Runs on meeting start/end (currently-running meetings, not just upcoming):
- **`AudioRouter`** — CoreAudio wrapper around `kAudioHardwarePropertyDefaultOutputDevice`. Lists output devices with their **UID** (stable across reboots) and transport type (so Bluetooth is identifiable). The Handoff config persists device *UIDs*, never `AudioDeviceID` (CoreAudio reassigns those on disconnect).
- **`FocusModeController`** — invokes user-installed Shortcuts via `shortcuts://run-shortcut?name=...` URLs. `INFocusStatusCenter` is read-only, AppleScript needs the Automation entitlement, Shortcuts is the only blessed escape hatch for a sandboxed app. After invocation, polls `INFocusStatusCenter` for up to 3s to verify; reports `.verified` / `.unverified` / `.noFocusPermission`. Users must install two named Shortcuts: `MeetingIntro – Start Focus` and `MeetingIntro – End Focus`.
- **`HandoffStateSnapshot`** — `Codable`, persisted to UserDefaults. Captures `(meetingID, endTime, priorOutputDeviceUID, priorFocusWasActive)`. The coordinator restores from this snapshot on the meeting-end event, and on next launch if a stale snapshot exists with `endTime <= now` (crash-recovery path).
- **`MeetingHandoffCoordinator`** subscribes to set-diff on `CalendarManager.$meetingsCurrentlyRunning`. On enter: snapshot + switch audio + invoke Focus. On exit: restore.

### Meeting recording (`Recording/`)

Same set-diff pattern as `SystemHandoff/`, gated on `meeting.url != nil` so meetings without a detected conference link are skipped:

- **`RecordingController`** — owns **two parallel audio pipelines** writing to a single `.m4a`. `SCStream` (ScreenCaptureKit) for **system audio** — the only public macOS API that captures app playback without a virtual loopback driver. `AVCaptureSession` + `AVCaptureAudioDataOutput` for the **microphone**. We'd prefer SCStream's own `captureMicrophone` (one stream, one writer), but that's macOS 15+ and our deployment target is 14.0. SCStream requires video config even when we only want audio, so we set a 2×2 placeholder at 1 fps and never wire up a video output. Output: dual-track `.m4a` — most players (QuickTime, VLC, Finder Preview) mix the two tracks on playback.
- **`SessionStarter`** — small threadsafe coordinator that calls `writer.startSession(atSourceTime:)` exactly once, using the PTS of whichever pipeline produces the first sample. Both pipelines wait on it before appending.
- **`RecordingSession`** — `Codable`, persisted to `UserDefaults["recordingSession"]`. Same crash-recovery pattern as `HandoffStateSnapshot`. On launch, if `meetingEndTime <= now`: partial files under 100 KB get deleted (empty container, no recoverable audio); larger files are left for manual recovery via QuickTime or ffmpeg (we can't `finishWriting()` from a different process).
- **`RecordingConfig`** — `isEnabled`, `hasAcceptedDisclaimer` (persists across off/on toggles so the legal disclaimer modal only fires once), `saveDirectoryBookmark: Data?` (security-scoped bookmark for user-picked non-default save folders; nil → defaults to `~/Movies/MeetingIntro/`).
- **`MeetingRecordingCoordinator`** subscribes to `CalendarManager.$meetingsCurrentlyRunning` set-diff. Gates on `config.isEnabled && config.hasAcceptedDisclaimer && meeting.url != nil`. Errors surface via `lastError: String?` for the Settings UI to render.

Permissions required (added to `project.yml` `info.properties` so they land in the generated `Info.plist`):
- `NSMicrophoneUsageDescription` — prompted on first `AVCaptureSession.startRunning()`.
- `NSScreenCaptureUsageDescription` — prompted on first `SCStream.startCapture()`.
- Entitlements: `com.apple.security.device.audio-input` (sandboxed mic); `com.apple.security.files.user-selected.read-write` (was read-only; upgraded so the folder picker bookmark works).

**Permission surfacing (v2.5.2):** Screen Recording is the silent killer — `SCStream` needs it for the system-audio ("Them") track, but the user is never prompted again after the first decline, so auto-record fails on every meeting with only an error in the log. `RecordingController.start` now **pre-flights** `CGPreflightScreenCaptureAccess()` (`hasScreenRecordingPermission`) before touching the filesystem, throwing `permissionDenied` cleanly instead of creating-then-deleting the output file. `MeetingRecordingCoordinator.beginRecording` checks the same up front and logs a **single** `.warn` per session (not an error every meeting) plus a clear actionable `lastError`. Settings → Recording shows a **Permissions** section (visible when auto-record is on) with green/orange status rows for Screen Recording + Microphone and a "Grant…" button that fires `CGRequestScreenCaptureAccess()` and deep-links to `x-apple.systempreferences:com.apple.preference.security?Privacy_ScreenCapture`. The rows re-read TCC state on `NSApplication.didBecomeActiveNotification` (via a `permissionTick` `.id()`) so granting in System Settings reflects without reopening the tab.

Filename format: `YYYY-MM-DD HHmm - {sanitized title}.m4a`. Sanitization strips `/\:?<>|*"`, collapses whitespace, truncates to 80 chars, suffixes `-2`/`-3`/… on collision.

### Transcription + meeting notes (`MeetingNotes/`, v2.4.0)

Post-processing pipeline: finished recording → transcript → AI notes. **The dual-track recording is the speaker-attribution trick**: stereo track = system audio (them), mono track = mic (you) — `AudioTrackExporter` identifies tracks by **channel count** (not order; verified empirically) and exports each to 16 kHz mono 32 kbps AAC (1 hr ≈ 14 MB, under Groq's 25 MB cap). Each track transcribes separately, segments merge chronologically with You/Them labels (same-speaker gaps < 3 s coalesce).

- **Engines** (`TranscriptionEngine` protocol): `WhisperKitEngine` — on-device via the **WhisperKit SPM package** (the app's first external dependency, declared in `project.yml` `packages:`; source-only so notarization is unaffected; instance cached per model; models download to Application Support on first use). `GroqWhisperEngine` — `whisper-large-v3-turbo` multipart upload, `verbose_json`. Key in Keychain (`groqTranscriptionKey`). **No silent engine fallback** — a surprise 1.6 GB model download is not a fallback; failures surface verbatim in JobState.
- **`NotesGenerator` + `LLMClient`**: notes written by the **Quick Add provider config** (shared; local Ollama = fully offline pipeline). `LLMClient` is deliberately separate from `OpenRouterParser` — the parser is tuned for the 6 s live-parse window with parse-specific error hints and was heavily field-debugged; the client uses 120-180 s timeouts and generic errors. Don't merge them.
- **`MeetingNotesPipeline`** (@MainActor): serial queue, publishes `jobs: [path: JobState]`. Auto-trigger via `MeetingRecordingCoordinator.stopAndEnqueueNotes()` — centralizes the capture-`currentFileURL`-before-`stop()` dance (stop nils it) and runs on meeting-end, manual, AND pre-sleep stops. Gated on `notesConfig.autoGenerate`.
- **Sidecars are the durable store**: `<name>.transcript.md` + `<name>.notes.md` next to the `.m4a`. `RecordingDocument` derives all status from file existence — no database.
- **Viewer**: `Window("Meeting Notes", id: "meetingNotes")` scene (menu bar ⌘M / Settings button; `openWindow` + `NSApp.activate`). List + Transcript/Notes tabs with lightweight per-line markdown rendering (`AttributedString(markdown:)` is inline-only — headers/tables handled manually).

**Visibility and lifecycle (v2.1.1):**
- Menu bar icon swaps to `record.circle.fill` while recording — at-a-glance signal that the active capture belongs to MeetingIntro vs some other app.
- Menu bar dropdown shows "🔴 Recording" + meeting title + inline Stop button at the top — manual stop without opening Settings.
- `NotificationManager.sendRecordingStartedNotification` posts a one-shot per meeting when recording begins (key `recording_started_<meeting.id>`).
- **Graceful app quit:** `AppDelegate.applicationShouldTerminate` returns `.terminateLater` while a recording is in progress, awaits `coordinator.stopManually()`, then calls `reply(toApplicationShouldTerminate:)`. Without this the `AVAssetWriter` is force-killed mid-write and the file is unrecoverable. The delegate is wired via `NSApplicationDelegateAdaptor`; `AppLifecycleManager.observe` injects the coordinator weak reference once the `@StateObject`s exist.
- **Sleep/wake:** `NSWorkspace.willSleepNotification` → `controller.stop()` so the file is finalized before macOS suspends `SCStream` and `AVCaptureSession`. `NSWorkspace.didWakeNotification` clears `runningMeetingIDs` + the snapshot and reconciles against the calendar's currently-running meetings, so a meeting that's still going across a sleep gets a fresh recording in a new file. `AVAssetWriter` has no resume API; a new file is the cleanest recovery path.

- **E2E self-test** (`FileOrganizer.runSelfTest`, `#if DEBUG`; run headless via `MEETINGINTRO_SELFTEST=1 <app-binary>` — hooked in `AppDelegate`): builds a temp tree and asserts gather/temp-ignore/packages/recursion, findDuplicates, apply move+trash+collision, reorganize prune, and undo — the automated gate for the filesystem logic (config = nil, never touches real data).

### Ticker — menu-bar news crawl (`Ticker/`, v2.16.0)

Third **opt-in plugin** (same pattern as File Organizer / Dictionary, **off by default**): a TV-chyron strip that crawls across the **empty middle of the menu bar row** — the spot that lines up with the webcam — cycling upcoming meetings, tasks due/overdue, unacknowledged cancellations, and (optionally) recording/auto-join status. Read-only over existing published state; it wires **nothing** into the reminder path.

- **`TickerConfig`** — every tunable (sources, `taskLookaheadHours`, `scrollSpeed` pt/s, `width`, the three auto-hide toggles), UserDefaults-persisted `didSet` like `QuickAddConfig`. `isEnabled` (key `tickerEnabled`) is bound directly by the Plugins card, so toggling it shows/hides live.
- **`TickerFeed.build(...)`** — pure state → `[TickerItem]` (id/symbol/text/semantic tint), most urgent first: cancellations → tasks → meetings → status. Nothing else decides content.
- **`TickerLeader` (v2.16.2)** — the character at the head of the crawl that hauls the text behind it: 20 options (🚂 🚚 🚀 🏃 🐈 🐕 🐌 🐢 🐜 🐝 🐎 🦖 👻 🤖 🛸 📰 📣 + SF-Symbol hare/tortoise/sparkles) plus `.none` (default, the original status-icons-only look). It fronts **each message** (v2.16.3 — it briefly led the strip as a whole, which the user rejected: "it should be in front of each message and not on it's own"), standing in for that item's status glyph, so every line gets its own character hauling it. Symbol leaders inherit the item's tint; emoji are colour glyphs and ignore it. `showItemIcons` therefore only applies when the leader is `.none` (the sheet disables the toggle otherwise). **Emoji orientation is load-bearing:** the crawl travels right-to-left, so a leader must face left; Apple's vehicle/animal emoji nearly all do. If you add a right-facing glyph, flip it with `.scaleEffect(x: -1)` or it appears to shove the text backwards. Companion settings: `showItemIcons` (off = leader is the only glyph) and `leaderBounce` (a CA-driven vertical bob). All presentation is bundled in `TickerStyle` (leader / showItemIcons / bounce / speed) so the window controller diffs it in one `!=` and only rebuilds the view when it actually changed.
- **`TickerView`** — the crawl. The strip is rendered **twice back-to-back** and offset by exactly one strip width (measured via a `PreferenceKey`), which is what makes the wrap seamless. **The offset is a repeating `.linear` animation handed to Core Animation, deliberately NOT `TimelineView(.animation)`** — a TimelineView would re-render the SwiftUI body every display frame, all day, on the menu bar. Don't "modernize" it.
- **`TickerWindowController`** — borderless non-activating `NSPanel`, three load-bearing properties: **level `.statusBar`** (the menu bar's own window sits just below — `.floating` would render it invisible up there), **`ignoresMouseEvents = true`** (it overlays the menu bar row, so taking clicks would eat clicks meant for app menus / status icons — click-through is the user's explicit design choice), and the **notch fallback**: when `screen.safeAreaInsets.top > 0` the strip drops just below the menu bar, because top-centre *is* the camera housing on those Macs. Re-centres on `didChangeScreenParametersNotification`.
- **`TickerCoordinator`** — attached in `observe()`; subscribes to `$todaysMeetings`, `$pendingCancellations`, `TaskManager.$tasks`, `$snapshot`, `RecordingController.$isRecording`, plus a 15s tick (the countdown *text* goes stale; the crawl itself is CA-animated, not timer-driven). Applies the auto-hide rules — **screen sharing** (default on: a crawl of your task titles across a shared screen is a real leak), **in a call**, **Focus on** — and hides entirely when the feed is empty, so the strip's presence is itself a signal. `hiddenReason` drives the Settings status line ("why can't I see it?"). `showPreview()` runs a 12s sample crawl because the real feed is often empty.
- **Settings → Plugins** holds only the card: toggle, live status line, and two buttons — **Ticker Settings…** (opens `TickerSettingsSheet`: sources / appearance / auto-hide) and **Preview the Ticker**. The three config sections were briefly inline on the tab and were moved behind the button at the user's request (v2.16.1) — the Plugins tab lists *what's available*; configuring one add-on at length there pushes the other plugins off screen. Keep new ticker options in the sheet.

### Self-update (`AppUpdater.swift`, v2.7.1, hardened v2.8.1)

Settings → About shows an update control beside the version. On a newer release `AppUpdater` runs `brew upgrade --cask templegit9/tap/meetingintro` **in-process** (via `/bin/zsh -lc`), then `open`s the upgraded bundle and quits to relaunch. **This works only because the app is NOT App-Sandboxed** — `MeetingIntro.entitlements` has the hardened-runtime/TCC entitlements (calendars, network.client, files.user-selected, device.audio-input) but no `com.apple.security.app-sandbox`, so spawning `brew` is permitted. If brew isn't found or the upgrade fails, it surfaces the manual `brew upgrade --cask meetingintro` command — never a dead end.

**Detection reliability (v2.8.1) — three fixes for "it doesn't always notice updates":** (1) **Query the releases LIST and pick the highest semver**, not `/releases/latest` — the latter lags on GitHub's CDN and depends on a "latest" pointer that can be wrong. (2) **Ephemeral, no-cache `URLSession`** (`requestCachePolicy = .reloadIgnoringLocalAndRemoteCacheData`, `urlCache = nil`) — GitHub sends `cache-control: max-age=60`, so the shared session could serve a stale "latest" and falsely report up-to-date right after a release. (3) **Proactive checks** via `startAutoChecks()` (called from the menu-bar label's `onAppear`): a silent check on launch + every 6h + on wake — previously it ONLY checked when the About tab opened, so a never-opened-About user never learned of updates. Background checks are **silent** (`checkSilently`): a flaky-network failure leaves the prior state instead of flipping to an error icon. The `updater` is a **shared App-level `@StateObject`** (was per-`SettingsView`) so an available update also surfaces as a row at the top of the **menu-bar dropdown** ("⬇︎ Update available — install vX"), not just in About. **(v2.8.3)** The About tab **always re-checks on open** (not just when state is `.idle`) — otherwise the launch auto-check leaves a stale `.upToDate` from before a newer release shipped and opening About wouldn't refresh it; and the `.upToDate` green check is now a **button** (manual re-check), since otherwise there's no way to force a check once a result is cached. **(v2.9.1)** A **"Check for updates automatically" toggle** (About; `@AppStorage(AppUpdater.autoCheckKey)`, default on) gates the background checks — `startAutoChecks()` is a no-op when off, and toggling calls `refreshAutoChecks()` to start/stop the 6h timer + wake observer live. Manual checks always work. About also shows the **build date/number** (CFBundleVersion is a YYYYMMDDHHmm release stamp, parsed to a date) and an SF-Symbol **link row** (GitHub / Releases / Feedback).

**Settings window front-ordering (v2.7.1, corrected v2.7.2):** keep the menu's "Settings…" as a **`SettingsLink`** — it's the only thing that reliably *opens* the SwiftUI `Settings` scene. (v2.7.1 briefly tried `NSApp.sendAction(showSettingsWindow:)` for the activation, but that selector isn't reliably wired in SwiftUI and, fired from a closing NSMenu's responder context, silently no-op'd — Settings stopped opening at all. Don't reintroduce it.) The bring-to-front (an `LSUIElement` app opens Settings *behind* other windows because the app isn't activated) is handled by **`SettingsWindowActivator`**, a background `NSViewRepresentable` inside `SettingsView` that calls `NSApp.activate(ignoringOtherApps:)` + `orderFrontRegardless` on first appear **and** whenever the window becomes visible again (`NSWindow.didChangeOcclusionStateNotification`, guarded on `!isKeyWindow`) — so re-open-while-buried works without re-fronting on every state change.

### Notification delivery + Diagnostics (`Diagnostics/`, v2.4.1)

**Load-bearing gotcha**: a menu-bar (`LSUIElement`) app is "active" whenever the user clicks into it, and macOS **silently drops notifications posted while the sending app is foreground** unless it sets a `UNUserNotificationCenterDelegate` and returns presentation options from `willPresent`. We shipped v1.0.0–v2.4.0 without one, so reminders + cancellation notices vanished whenever MeetingIntro had focus. `AppDelegate` (in `MeetingIntroApp.swift`) now conforms to `UNUserNotificationCenterDelegate`, sets `UNUserNotificationCenter.current().delegate = self` in `applicationDidFinishLaunching`, and `willPresent` returns `[.banner, .list, .sound]`. **Do not remove this.** `NotificationManager` also stores the auth result in `@Published authorizationStatus` (was discarded) so a denied permission is visible instead of silently failing.

**`DiagnosticLog`**: app-wide `@MainActor ObservableObject` (injected explicitly in `observe()`, no `.shared`). In-memory ring (2000) + daily rotating file in `~/Library/Application Support/MeetingIntro/Diagnostics/`, **7-day retention pruned both on launch and once per calendar day** (a never-quit menu-bar app wouldn't prune on launch alone — the per-day check on write covers it). Verbose, always-on; `Category` + `Level` tagged. Every suppression logs its reason (dedup / freshness gate / smart-context hold / notifications-disabled / delivery error) — this is the triage trail when "it didn't fire."

**Hidden Diagnostics tab** (Android developer-options mechanic): `SettingsSection.diagnostics` is filtered out of the sidebar until `diagnosticsUnlocked` (UserDefaults) is set by tapping the version line in About **3×**. The log captures regardless of tab visibility; a "Hide Diagnostics" button re-hides. The tab shows a live filterable stream + a notification-authorization banner with an Open-System-Settings deep link.

### Graph verification — a second opinion on Exchange events (`CalendarSync/GraphVerifier.swift`, issue #23, v2.20.0)

macOS Calendar's Exchange sync can fail to apply a change and leave a **phantom**: a meeting cancelled on the server that EventKit still reports as live, with `status != .canceled` and no title prefix, so **nothing local can distinguish it**. The reported case reminded a user about a meeting cancelled a week earlier and then auto-joined him into a Zoom that didn't exist. The only fix is to ask the server.

- **A verifier, NOT a provider switch.** The app runs one provider at a time, so switching to Graph would drop every non-Exchange calendar in macOS Calendar. EventKit stays the source of truth for display; Graph answers only "does the server still have this?" for events where `MeetingEvent.isExchangeBacked` (set at the EventKit boundary from `EKSource.sourceType == .exchange`).
- **Verdicts**: `.confirmed` / `.cancelledUpstream` / `.absentUpstream`. Suppressing verdicts feed `CalendarManager.upstreamGate` — same shape and the same gate sites as `responseGate` (overlay where-clause, the "why no reminder" diagnostic) **plus `evaluateAutoJoin`**, since opening a phantom's link is the exact harm.
- **Every rail points at "never suppress a real meeting"** — do not weaken these: a **failed or empty** Graph fetch aborts the run (treating "server returned nothing" as "everything is cancelled" would silence a whole day); a suppressing verdict needs **two consecutive agreeing runs** while `.confirmed` clears immediately; only Exchange-backed, non-all-day, non-cancelled events are candidates. The two-run rule doubles as grace for a locally-created event that hasn't synced upstream yet.
- **Matching** is by normalised title + start minute (`matchKey`) because Graph and EventKit ids are unrelated: lowercased, whitespace collapsed, `Canceled:`/`Cancelled:` prefix stripped (one side often carries it). Verified: tolerant of case/spacing/prefix and a 30s start difference, and does **not** collapse same-title meetings 30 min apart.
- **Runs every 5 min** (`runInterval`), driven by a `$upcomingWeek` subscription — **not** `onPollComplete`, which `CalendarMirrorEngine` already owns as a single closure (assigning it there would silently disable mirroring).
- Opt-in (`GraphVerifierConfig.isEnabled`, default off) under Settings → Calendar → "Verify against Microsoft 365"; requires the Graph sign-in above. **Note the deployment reality:** since Microsoft's managed consent policy (Oct 2025, extended June 2026) even `Calendars.Read` needs **admin consent** in default tenants, so enterprise users need IT approval regardless of scope.

### Calendar mirror / sync (`CalendarSync/`, v2.5.0)

One-way continuous mirror: source calendar(s) → a destination, every poll. **The app's first autonomous recurring write to real calendars** — treat changes here with the caution that implies.

- **State lives in the calendar, not a DB.** Each mirror event carries `event.url = meetingintro-mirror://<mirrorID>/<base64 sourceID>` (`MirrorMarker`). Reconcile = diff source events against destination events bearing this marker. **Only marker-carrying events are ever modified/deleted** — real events are untouchable. This survives reinstall and never drifts.
- **`CalendarMirrorEngine.reconcileAll()`** rides `CalendarManager.onPollComplete` (the 30s poll). Per mirror: fetch sources in a 30-day window (all-day included; marker-carrying events excluded → no mirror-of-mirror), diff by source id, create/update/delete, single batched `eventStore.commit()`.
- **Three guardrails — do not weaken without re-review**: (1) marker-only-touch; (2) **delete circuit-breaker** — a reconcile removing >50 copies OR >90% of existing copies *pauses* the mirror (sets `paused`) instead of executing, guarding against a source transiently returning zero events. **It has a one-shot escape hatch (`Mirror.approveLargeChangeOnce`, v2.19.2) and needs one**: the breaker can't tell a transient empty source from the user deliberately changing which calendars are mirrored, where mass deletion is the correct outcome. Before the flag it was a trap — re-saving or Re-enable cleared `paused`, the next reconcile found the same orphans and re-paused, so the mirror could never converge (seen in the wild: 80/98 copies, 16 pause WARNs in 81s, the user clicking Re-enable seven times in a second). Approval is granted by an edit that changes `sourceCalendarIDs`/`destinationCalendarID` (a rename does NOT grant it) or by "Re-enable and sync", whose message states the count first — then consumed by the next reconcile. **The field is `Bool?` on purpose:** a non-optional addition throws `keyNotFound` on mirrors persisted by earlier builds and silently loses the user's configuration (verified, not assumed); (3) every action logged to `DiagnosticLog` (`.calendar`).
- **Idempotent writes — do NOT regress (v2.9.5):** `writeMirror` returns `MirrorWriteResult` (created/updated/**unchanged**) and **only saves when a field actually differs** from the existing copy; the engine **only commits when created+updated+deleted > 0**. Without this, every reconcile re-saved all N copies (observed: "+0 ~171 -0" every poll), and each commit fired `EKEventStoreChanged` → another refresh → another reconcile — a churn/feedback loop (and on **two devices sharing one iCloud destination, they fight forever**). A steady state must settle to no writes/no commit. `lastSync` still stamps every reconcile.
- **Mirror-copy de-dup in the app's own views (v2.9.5, corrected v2.9.6):** `EventKitProvider.fetchUpcomingEvents` de-dups mirror copies **only when they're true duplicates** — a copy (carrying a `MirrorMarker` url) is dropped **only if its source event is also in the fetch** (`presentSourceIDs.contains(decoded.sourceID)`), i.e. you monitor both source and destination. If you monitor **only the destination** calendar, the copy is your sole view of that meeting → **kept**. ⚠️ **v2.9.5 regression (do not reintroduce):** it blanket-stripped *every* marker-carrying event, which **zeroed out a calendar that holds only mirror copies** — a user who monitored their "Personal → Work" mirror's destination saw an empty app while Calendar.app showed events. The fetch logs an `EventKit fetch: N timed, M mirror copies, K dropped → … kept` line when copies are present. (`mirrorSourceEvents` still excludes markers on the source side to prevent mirror-of-mirror.)
- **Engine + CalendarManager share ONE `EventKitProvider`** (hence `eventKitProvider` is internal, not private) — an EKEvent fetched from one `EKEventStore` can't be saved via another.
- **Destinations**: new dedicated calendar (EventKit can only create on **iCloud or Local** — Google/Exchange reject `saveCalendar`; the UI tells users to create the calendar there first and mirror into it as an *existing* destination) or an existing writable calendar (read-only/subscribed rejected). Detail mode: `full` or opaque `busy`. Attendees never copied (EventKit limit, same as Quick Add).
- Late-wired like the coordinators: `mirrorEngine.attach(config:calendarManager:)` in `observe()`.
- **`MirrorEditSheet` loads its own calendar list** (via a `loadCalendars` async closure), not a snapshot from the parent tab's `@State`. Earlier it took `calendars: quickAddCalendars`, which the Calendar Sync tab populated in a `.task`; opening **Add Mirror** before that async fetch returned left the Sources list empty, so Create silently failed the "pick at least one source" guard and **no mirror persisted even though the user may have created the destination calendar** (v2.7.4 fix — the reported "created a mirror but it doesn't show" bug). Create is disabled until the load completes. The save/delete UI path (`SettingsView.saveMirror`/`deleteMirror`) now logs to `DiagnosticLog(.calendar)` — previously the entire mirror save path was silent, making this class of failure undiagnosable from the log.

## Conventions

- **No hardcoded values.** Every tunable lives in `UserDefaults` (or Keychain for credentials). If you add a feature, add a setting.
- **SwiftUI-first.** Drop to AppKit only where SwiftUI genuinely can't do the job — currently `OverlayWindowController` (NSPanel), `NSOpenPanel` for audio picking, and `NSWorkspace.shared.open` for URLs/Shortcuts.
- **`@MainActor` on managers that touch published state.** All managers in `MeetingContext/` and `SystemHandoff/` are main-actor isolated. CoreAudio listeners dispatch back to main via `Task { @MainActor in ... }`. `deinit` cannot call `@MainActor` methods — for singletons that live for app lifetime, just skip explicit cleanup.
- **Single wiring point.** New cross-service subscriptions go in `AppLifecycleManager.observe`.
- **`.entitlements` and `Info.plist` are configured in `project.yml`, not edited directly.**
- **Settings text fields use `.textFieldStyle(.roundedBorder)` (v2.9.7).** In a grouped `Form`, a bare `TextField("placeholder", …)` renders the placeholder as a *left label* with an invisible, right-aligned input region — users can't see where to type. Every `TextField`/`SecureField` in `SettingsView` and its sheets (`TemplateEditSheet`, `MirrorEditSheet`) sets `.roundedBorder` so the input is a visible box with the hint inside. (The Quick Add palette `QuickAddView` is deliberately `.plain` — it's not a Settings surface.)
- **Settings explanatory hints live behind a section-header ⓘ (v2.9.7).** The grouped Form was cluttered with `.font(.caption).foregroundStyle(.secondary)` "what this does" captions under nearly every section. They now move into `SettingsSectionHeader(_ title:, info:)` — a header view with an ⓘ button whose **click→popover** markdown-renders the text (one ⓘ per section; multiple captions merged with `\n\n`). Pattern: `Section { rows } header: { SettingsSectionHeader("Title", info: "…") }`. **What stays inline (do NOT bury behind the ⓘ):** permission/authorization warnings + status, error/colored text, dynamic status (interpolated counts, "synced Xm ago", test results), and destructive/legal warnings — they shouldn't be a click away. New explanatory prose for a setting goes in the section's `info:`, not a body caption.
